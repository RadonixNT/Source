Time Locks and Board Information

Read the controller's dated locks and board information, understand their effect on operation, and follow the authorized management procedure.

Expanded draft for review. This chapter describes the reviewed implementation. Lock and clock changes are persistent board operations.

26.1 Understand what a dated lock restricts

A time lock is a dated record held by the controller board. When its due date is reached according to the board clock, the controller restricts new ToolPath runs. A ToolPath run is the controller's execution of a prepared movement path, such as a machining program. The lock is separate from the Operator and Engineering passwords used to enter application access levels.

The form states Due dates block new runs. Running work continues. A path already running is not stopped merely because a lock becomes due. Other movements remain available under their normal operating conditions. This means that a time lock is not an emergency-stop function, a guard interlock or proof that the machine cannot move.

A due date is a calendar boundary

The application compares the registered date with the controller board's calendar date. A lock dated today is already due; it is not a promise that use continues until the end of that day. If more than one lock exists, any due entry can keep new runs restricted. Removing one entry therefore does not establish that every restriction has been cleared.

A warning that a lock is due tomorrow provides time to contact the responsible person. It does not remove the date or change the password. Report it before the next planned production period rather than discovering the restriction when a new job is ready to start.

Do not use available manual movement as an improvised replacement for a blocked production run. The lock defines an administrative restriction, while ordinary operating procedures still define how the machine may be used. Likewise, do not change the computer date as a trial repair: the lock is evaluated using board state and clock management has its own controlled process.

The operator's first task is to identify and report the condition accurately. Record whether the message concerns a due lock, an invalid clock, unavailable information or storage corruption. Management actions in this chapter are for a person with the required access and authorization; reading about them does not make a persistent board change part of ordinary job setup.

26.2 Open Time locks and read the list and board information

Open Configuration with accepted Engineering access, then use the time-lock toolbar action. The window is titled Time locks. The application requires both Engineering access and an available authenticated physical controller board for this action. Operator access alone is insufficient. Simulation does not satisfy the physical-board requirement.

If the action is unavailable, check those requirements before assuming the board has no locks. An unavailable button says nothing about how many lock records exist. Use Chapter 25 for the access process and the normal connection procedure for the controller. Do not connect or change operating mode solely to explore a form during production.

Read the three areas in order

The left area lists Registered locks, with a count out of 24. Entries are sorted by due date. The upper-right MM information area shows board date, time, runtime, manufacturing date and firmware. The lower-right Manage locks area contains the date and password fields with Add and Delete. Sync clock belongs to the information area; Close is in the footer.

Table 26-2. Lock-list status text

Due tomorrowThe due date is the next calendar day according to the board.
DueThe due date is today or earlier.

No locks registeredA successful available snapshot contains no lock entries.
Lock information unavailableThe list was not successfully established; this is not an empty-list confirmation.

Selecting an existing entry copies its date into the date field and clears both lock-password fields. Selection does not remove or modify the entry. The passwords are not displayed in the list. If you need to remove that entry, obtain its specific lock password through the authorized process.

Interpret board information without inventing missing values

Board date and Board time are the controller clock reading, displayed as a full year-month-day and hours:minutes:seconds. Board runtime is shown in hours, minutes and seconds. It is a board runtime record, not the current program's elapsed time, an estimate of remaining cutting time or the age of the computer session. Manufacturing date is a separate recorded date. Firmware identifies the software running on the board.

Not recorded for manufacturing date means that a successful read found no recorded date. Unavailable means that the value could not be established. An unavailable runtime must not be reported as zero hours, and unavailable firmware must not be treated as an empty version that can be ignored.

These fields are informational in this form. There is no manufacturing-date editor or firmware-update control here. For service identification, also record the machine identity and, where required, the controller's MM UID from the Configuration reference; the lock form's information panel does not itself show that identifier.

26.3 Review the board clock and synchronize it only when authorized

The board clock determines whether a registered date is still in the future. The computer clock supplies the new local date and time when you select Sync clock, but it is not simply substituted every time the lock window refreshes. Reading the form does not synchronize either clock.

Before an authorized synchronization, stop motion through the normal procedure and establish the approved maintenance condition. Check the computer's displayed calendar date and local time against the site's correct time. The operation copies the computer's local date and time. It is not a time-zone selection dialog, and the form does not ask you to type a replacement board date manually. The supported calendar is the Gregorian calendar from 2000 through 2099.

The lock list must be successfully empty

Sync clock is available only when the application has an available lock snapshot with zero entries, the required access is present and no operation is busy. If any lock remains, the form says Remove all locks before synchronizing the clock. This is a restriction on the operation, not an instruction to delete legitimate locks merely because the displayed time looks inconvenient.

Any removal needed for an approved clock-service task must itself be authorized and use the correct date and password for every affected entry. Preserve the approved record and the intended final configuration. Do not replace lock management with attempts to move a date backward.

Synchronize before adding the first lock

The form requires a successful synchronization in the current dialog before it allows the first lock to be added to an empty list. A plausible date already visible on the board is not sufficient for this first-entry rule. Select Sync clock, review its confirmation, then wait for Controller clock synchronized with this computer.

The synchronization confirmation belongs to this dialog's current valid state. Closing and reopening the form loses that confirmation. Deleting a lock also clears it; after deleting the final lock, synchronize again before an approved first replacement entry. A failed operation or loss of access can similarly invalidate the confirmation.

Clock synchronization is a persistent board operation. It is not undone by closing Time locks or by cancelling the parent Configuration window. If the status says the clock could not be synchronized or did not start advancing, do not assume the copied value has been accepted. Report the condition and have the board clock checked.

The form displays snapshots and refreshes approximately once per minute while available. A time label that stays unchanged between refreshes is not, by itself, proof that the board clock stopped. Use the operation result and subsequent successful readings, rather than expecting this information panel to behave like a second-by-second wall clock.

26.4 Enter a valid date and add an authorized lock

Adding a lock creates a persistent future restriction on new runs. Do this only as an authorized administration task, with motion stopped, the approved maintenance condition established, an agreed date and a secure way to retain the lock password. A practice entry on a production controller is a real lock, even if it is described verbally as a test.

Read the date format carefully

The Date field is labelled Date (YY/MM/DD). YY is the final two digits of the Gregorian year, MM is the month and DD is the day. For example, 27/03/15 means 15 March 2027. This example demonstrates the format only; choose the approved future date for the actual task.

Table 26-4. Accepted date and password input
ItemAccepted formImportant limit

A date today or earlier than the valid board date is rejected. A second lock for an already registered date is also rejected. There can be at most 24 registered locks; Add becomes unavailable when that capacity is reached. Do not remove another entry to make space without reviewing its purpose and obtaining authorization.

Add in a controlled order

  1. Confirm the approved date, the correct machine and the required Engineering access.
  2. Read the current lock list and board date. If the list is empty, complete the current-dialog synchronization procedure first.
  3. Enter the date, Lock password and Confirm lock password.
  4. Review the date again, especially the order of year, month and day.
  5. Select Add once and wait for the submitted operation and reread to finish.
  6. Look for Lock saved. and verify that the intended date appears in a successfully refreshed list.

The password is associated with that lock date. It is not the Operator, Engineering or Manufacturer account password merely because those accounts also use passwords. The list does not reveal the lock password later. Record the administrative facts in the service record and retain the secret through the agreed secure process.

The form clears the password fields after a submitted change attempt. A validation message before submission, such as a mismatch or duplicate date, means the input needs correction. If the board operation fails or its result is unknown, do not assume that no lock was written. Wait for a successful refresh and inspect the actual list before another Add.

A completed Add is saved immediately on the board. Parent Configuration Cancel is not an undo button for it. There is no ordinary “edit this lock's date” action here: changing an existing record requires separately authorized removal and addition, with each result checked.

26.5 Remove the intended lock and verify the remaining restrictions

Delete permanently removes the lock for the entered date when its lock password is accepted. It does not disable all locks, sign out of Engineering access or replace the Manufacturer password. The operation must be authorized for the specific entry, including when the entry is already due.

Prepare for all lock and clock changes with motion stopped and the machine in the approved maintenance condition. These are board changes, and the controller handles the required temporary connection reconfiguration and authentication. If a message says stopped motion or maintenance mode is required, resolve that condition through the normal service procedure. Do not search for a way to force the button while motion is active.

Selection helps prevent deleting the wrong date

  1. Read the successfully loaded list and identify the exact entry to remove.
  2. Select it. Confirm that its date has been copied into the Date field.
  3. Enter that entry's Lock password. Selecting the entry clears previous password text, so enter it after selection.
  4. Review the date and authorization once more, then select Delete.
  5. Wait for the result and the list refresh.
  6. Look for Lock permanently removed. and verify that the intended date is absent from an available list.

Deletion uses the date in the input field, not merely whichever row looks highlighted. If you edit that field after selecting a row, check it carefully before Delete. A valid date that is not registered produces No lock is registered for this date. An incorrect date/password pair can be rejected by the board even when the password has the required eight-character format.

After removing a due entry

Read the entire remaining list. Another due lock, an invalid clock with remaining locks or a storage fault may still prevent new runs. Confirm the controller's current status before planning a new program. Removing a lock does not automatically start a program or resume an interrupted one.

If the final entry was removed, clock synchronization becomes eligible when the empty list has been successfully read. The previous synchronization confirmation has been cleared. If the authorized task also calls for adding a new first entry, synchronize the clock again in this dialog before attempting Add.

If the password is unavailable, stop at reporting the date and status to the responsible person. The form does not offer a universal removal password or a local-account substitution. Do not delete other known entries, change the computer calendar or repeatedly try unrelated account passwords in an attempt to clear the restriction.

Record the removed date, the authorizing person and the confirmed result without recording the secret. If the result is unknown, inspect the refreshed list before retrying. An unavailable list must never be accepted as evidence that the deletion succeeded.

26.6 Interpret refreshes, unavailable data and operation failures

The form reads information when it opens and refreshes automatically every 60 seconds while visible and available. It skips a scheduled refresh while another operation or the clock-confirmation dialog is in progress. The footer's Updated time is the computer's time of the successful display update; it is not the board-time field itself.

Automatic refresh preserves typed lock input and the selected date where possible. It does not submit Add or Delete. A refreshed row can change from Scheduled to Due tomorrow or Due as board dates change, but the display's timer is not what enforces the controller restriction. Closing the window does not stop lock enforcement.

Partial information can still be valid

The lock/clock read and the additional board-information read are handled separately. A firmware or runtime read can fail while the lock list remains available, or lock information can be unavailable while some board information is successfully displayed. Report the failed field specifically instead of describing every value as invalid.

Wait for the outcome, then inspect state

During a submitted operation the shared security dialog shows Working and prevents competing input and user closing. A timeout or connection interruption does not prove that a persistent board operation was cancelled. The board may have accepted a change before its result could be confirmed on screen.

After a failure, the form invalidates its lock snapshot and synchronization confirmation. It marks lock data unavailable and schedules automatic retries. You can also close and reopen the window once it is no longer busy to request a fresh read. There is no separate Refresh button in this form. For an uncertain Add or Delete, compare the resulting available list with the intended date. For clock work, inspect the valid board date/time and the diagnostic result.

Report enough information for service

Record machine identity, date of the incident, exact message, operation attempted, intended lock date, displayed board date/time, lock count and status, and whether the last read succeeded. Include available firmware and runtime information when requested. Keep lock passwords out of the report and screenshots.

Do not interpret a cleared display after a disconnect as a successful deletion. Do not interpret an available Add button as proof that every validation will pass. The form checks input when the action is requested, and the board independently accepts or rejects the change. Return the machine to production only after the responsible person has established the intended persistent state and the normal operating checks are satisfied.
