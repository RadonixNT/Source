Graphs, Scope and Communication Diagnostics

Observe axis motion and controller timing, understand communication-health information and prepare clear evidence for support.

Expanded draft for review. These tools observe activity. Pause and Clear in a graph are not machine stop or alarm-reset controls.

31.1 Choose and open the appropriate diagnostic window

A graph shows how a quantity changes over a short period. Instead of showing only the latest number, it draws a line through a series of observations. This can help describe a hesitation, a change in speed or an irregular controller cycle. You do not need to program the machine to collect a useful graph, but you do need to know what is being plotted and which display settings were used.

There are three relevant windows. Two are dedicated to particular questions; the general scope can switch between velocity and timing. Their controls and capture behavior are not identical. Start by identifying the window title rather than assuming that every graph follows the same instructions.

Use the application's current command assignment. Keyboard shortcuts can be changed or disabled; see Chapter 24 if the supplied keys do not open the expected window. The general scope's opening command is unavailable while the controller reports busy. Do not interrupt a machining operation merely to open it. The dedicated graph commands do not have that same busy condition, but ordinary access controls still apply.

Keep observation separate from machine operation

These windows open alongside the main application. Opening a graph does not start a controller connection, run a program or move an axis. It also does not stop an operation already in progress. Keep the normal controls and your view of the machine available. If the machine behaves unexpectedly, use its normal stop procedure; do not look for a motion-stop function in the graph.

Opening an already-open dedicated graph brings that window forward and restores it if minimized. You can resize the dedicated windows to make the graph, axis list or health table easier to read. When the application's window-layout preference is enabled, the dedicated graphs can restore display choices such as the time window and selected axes. Therefore, check the settings on screen instead of assuming every opening starts at the defaults.

Record the operating mode before drawing conclusions

A velocity trace in simulation can be useful for practice, but it does not demonstrate real motor response. The dedicated timing window explicitly reports that jitter is unavailable in hard simulation and does not provide a physical EtherCAT assessment there. EtherCAT is the communication network between the controller and its connected devices. A simulated session cannot verify its cables, devices or real-time performance.

Timing observation also enables timing telemetry while the relevant diagnostic tool is active. This is measurement activity, not a motion command or a repair. Close tools you no longer need. The dedicated velocity window does not itself request timing measurement; the general scope does so even when it is displaying velocity. These differences are another reason to include the exact window title in a support report.

31.2 Read the dedicated axis-velocity graph

Velocity is the rate and direction of movement. Position answers “where is the axis?”; velocity answers “how quickly, and in which direction, is its reported position changing?” In the Axis velocity window, the vertical direction represents velocity and the horizontal direction represents recent time. The right-hand end is labelled Now. Older observations are toward the left.

Identify the axis before reading its trace

The Axes list uses axis numbers, not necessarily the familiar X, Y and Z names on the operating screen. Obtain the number-to-name relationship from the accepted machine setup or support instruction. Do not assume that a particular number always means the same physical axis on every installation. The list includes existing axes, and its colored entries identify their corresponding graph colors.

Check the axes you want to display and uncheck unrelated axes to reduce overlapping lines. This changes the graph only; it does not enable or disable a motor. A trace is drawn only for an axis that is selected, exists and reports servo on. An axis can therefore be listed and checked without producing a trace. Do not turn a servo on merely to make a line appear.

Compare actual and target

For each axis, the solid line is actual velocity and the dashed line is target velocity. Both use the same axis color. Actual velocity is calculated from changes in reported actual position; target velocity is calculated from changes in target position. These are observations of controller feedback, not a separate measurement at the cutting edge.

A positive value represents movement in that axis's positive direction; a negative value represents its negative direction. A line near zero means little reported position change over the sampled interval. It does not establish a safe machine state by itself. The values are in axis units per second. If an axis is configured in millimetres, 10 units/s corresponds to 600 mm/min. Do not compare the graph directly with a per-minute feed display without accounting for this difference.

The available scale multipliers run from 0.001x to 1000x, with 1x as the initial choice. Changing scale does not change feed, velocity limits or tuning. The range can also change when you select a different set of active axes. Two screenshots with different range settings may make the same movement look very different.

Describe a difference without guessing its cause

During acceleration, steady travel and deceleration, compare the solid and dashed traces. Record a sustained separation, repeated oscillation or unexpected discontinuity with its axis, scale and operating condition. The graph does not identify the cause on its own. Do not adjust servo parameters, axis scaling or mechanics from a screenshot alone.

A trace pressed against the top or bottom border may exceed the selected display range; the drawing clips values at the boundary. Increase the range when appropriate and record the change. A blank graph, meanwhile, can mean no selected active axes, too few samples, a connection problem or a rendering problem. It is not automatically a zero-velocity measurement.

31.3 Use Pause, Resume and Clear in the dedicated graphs

The dedicated velocity and timing windows share Time (ms), Pause and Clear controls. Their purpose is to make observations easier to read. None of them stops the controller, resets an alarm or changes the machine's movement. Treat the normal machine controls and the graph controls as two separate sets of actions.

Pause freezes the presentation

Click Pause when an interesting condition is visible. The button changes to Resume and the dedicated graph reports Paused — display frozen. The trace stays available for inspection, but sampling continues while this graph remains active. In the timing window, the displayed health information is also frozen during this pause. A favorable assessment left on screen is therefore historical, not a continuing confirmation of network health.

Pause is useful for capturing a screenshot without the trace moving away. Include the paused status in the image and note when the event happened. Do not use frozen values to supervise a machine that is still running. If the machine itself needs to stop, use its normal stop control first.

Click Resume to return to recent live data. The graph does not slowly replay everything that happened while you were paused. It has a finite recent-sample buffer, and older observations are replaced as new samples arrive. A long pause is not a way to record a long unattended test.

Clear starts a new local observation

Clear removes the dedicated window's visible traces and establishes a new observation starting point. In the timing window it also resets the display's local observation baseline. New traces appear as subsequent samples arrive. If the graph remains paused, click Resume when you are ready to see them.

Clear affects this window's observation, not another open graph. It does not reset the underlying communication fault counters, erase the controller's faults or repair a missed deadline. Record useful evidence before clearing. A communication warning that remains after Clear can be reporting earlier faults accumulated in the same controller session.

Distinguish sampling from screen refresh

The dedicated graph footer describes 1 ms samples; the display itself redraws at an intended interval of about 33 milliseconds, and status information is normally refreshed less frequently, about every half second. Several samples can therefore arrive between screen updates. A temporarily stationary-looking display is not proof that the machine has stopped.

The horizontal time scale assumes the nominal sample interval. It is not an independent wall-clock recording with a timestamp on every plotted point. Connection changes discard the preceding session's captured data in the dedicated graphs. Minimizing and restoring also starts a fresh local observation, even if another diagnostic window continued collecting samples.

Set the time window and scale while live, wait for the required interval to fill, then pause to inspect it. Changing settings while paused does not produce a newly sampled picture. If the purpose is a before-and-after comparison, keep the same axes, range and time window in both captures, and state any unavoidable difference.

31.4 Understand cycle timing and the deadline statistics

The controller carries out its repeated control work in short cycles. The nominal cycle is 1000 microseconds, which is one millisecond or one thousandth of a second. A timing graph helps show when that work starts and finishes relative to the scheduled cycle boundary. The word jitter refers here to variation in that timing; it is not a measurement of vibration at the machine.

Open Jitter / EtherCAT health. The health table is on the left and the timing graph on the right. The legend identifies the solid line as cycle start and the dashed line as cycle end, both in microseconds. Select a time window appropriate to the observation. Unlike the dedicated velocity window, this window has no Y-scale selector.

Read offsets rather than assuming the line is cycle length

The start value is an offset from the scheduled boundary. A negative start value means early; a positive one means late. The end value is the finish offset from that same boundary. Subtracting start from end gives the measured time spent doing the cycle work. The finish offset alone is not the work duration.

For example, suppose a sample starts at 20 microseconds and ends at 180 microseconds. The observed cycle work takes 160 microseconds, and the finish leaves 820 microseconds before the next nominal boundary. This is an explanation of the quantities, not a pass limit or a measured result from your machine.

The table and the drawing answer different questions

The drawing uses a fixed vertical range of −50 to 350 microseconds. Values outside it are clipped at the border. A line against the top edge does not tell you the true peak, and a deadline crossing at 1000 microseconds cannot be read directly from that plotting range. Use the numerical statistics and assessment message rather than trying to estimate a large event from the clipped trace.

The minimum, mean, maximum and deadline count describe the available samples in the displayed window. They are not the worst results since the machine was switched on. Changing the time window changes the group of samples being summarized; an event eventually leaves the window. Capture it promptly and retain the window setting with the evidence.

Check freshness and mode

The assessment can say that timing samples are missing or stale even while old numerical information remains visible. Values remaining on screen do not guarantee that fresh measurements are arriving. In hard simulation, the window reports Simulation — jitter unavailable and does not draw a hardware timing trace. A dash is unavailable information, not a measured zero.

If the assessment reports Cycle deadline reached — inspect timing / CPU load, record the visible statistics and machine activity for support. The message identifies an observed timing condition; it does not identify its cause. Do not change the controller period or computer configuration as an operator response to a single graph. Follow the site's response procedure and preserve the evidence.

31.5 Read EtherCAT health without misinterpreting the counters

The communication part of Jitter / EtherCAT health helps answer whether the controller reports an operational network, whether receive and transmit activity are advancing, and whether faults have been recorded. It does not replace an electrical inspection or prove that every sensor, actuator and safety function works correctly.

RX means receive and TX means transmit. In this table, a successful “job” is a successful runtime receive or transmit operation. It is not necessarily one individual frame or one device update. WKC, the working counter, is an EtherCAT consistency check that compares reported participation with what was expected. A WKC mismatch helps identify a communication problem but does not, by itself, name the faulty cable or device.

Table 31-5. Communication rows and common interpretation mistakes
RowWhat it reportsWhat not to infer
EtherCAT state / requestedThe current master state and the requested state. OP means operational.A requested OP state is not proof that the current state has reached OP.
RX / TX successful jobsAccumulated successful receive and transmit jobs.These are not counts of individual devices or cutting operations.
RX / TX jobs per secondActivity calculated since the preceding display observation.This is not a packet-loss percentage or a fixed guaranteed frame rate.
RX missing / failed jobsReceive jobs reporting missing cyclic frames or a processing error.Do not equate each count with a unique physical cause.
TX lost jobs and TX errorsReported lost/failed transmit activity and transmit errors.These may overlap; adding them can count the same problem more than once.
WKC fault notificationsNotifications of working-counter mismatch.This is not the number of individual failed device-data items.
Last WKC actual / expectedThe values captured by the most recent WKC fault notification.The pair can remain unchanged after recovery; it is not necessarily the present live mismatch.
Master job errorsAn aggregate of runtime job errors.It overlaps other error counters and must not be added to them as a separate fault total.

Look for progression as well as totals

A large successful-job total mainly tells you that activity has accumulated. To describe current communication, observe whether both totals continue increasing and whether the displayed rates appear. The first rate observation can be a dash because a preceding reading is needed for comparison. Rates can also restart after a connection or counter reset.

Fault counters are session telemetry totals, whereas the timing statistics describe a recent sample window. A fault total that stays at 1 and a total that increases from 1 to 20 are different observations. Record both the total and whether it changed during your observation. Do not add the fault rows together, and do not repeatedly clear the graph expecting them to disappear. Clearing this display does not reset those underlying counters.

Read the assessment as a summary with limits

The text above the table gives the highest-priority condition selected by the view. It may report offline operation, simulation, disabled timing telemetry, a network not in OP, stale samples, a reached cycle deadline, recorded communication faults or waiting for receive/transmit progression. More than one issue can exist; a single message does not mean the other rows are irrelevant.

The favorable production assessment states Production RT — OP; traffic advancing; no reported faults in telemetry. Read those words literally: the observed telemetry meets those conditions. This is not a certificate of machine safety, proof of correct wiring or a guarantee that an intermittent fault cannot occur later. An engineering-mode message explicitly says that production real-time operation has not been assessed.

If Communication faults recorded — inspect counters remains after apparent recovery, inspect which totals are nonzero and whether they continue growing. The view can retain that assessment because faults were recorded earlier in the session. Do not reconnect merely to erase the evidence. Preserve the table, note the time and report the circumstances through the normal support process.

Hover over a parameter row for its explanatory tooltip. Enlarge the window or scroll the table to read all rows. When reporting a fault, include the current/requested state, the affected counters and their progression, rather than sending only the short assessment line.

31.6 Use the general diagnostic scope and recognize its differences

The window titled NT Diagnostic Scope contains Velocity and Jitter buttons, sliders for display scale and time, and Pause and Clear buttons. It is a separate tool from the dedicated graphs described above. Use it when a support instruction specifically asks for this scope, and include its title in every capture.

Choose the displayed quantity

Velocity shows actual and target velocity for existing axes that report servo on. Unlike the dedicated velocity window, this scope does not provide an axis-selection checklist. Actual and target traces use the same axis color with different opacity. Do not apply the dedicated window's solid/dashed legend here. If identifying an individual axis is difficult, use the dedicated velocity window and its numbered list for a clearer observation.

The Y slider changes display magnification. Its middle setting is 1x; the endpoints are 0.1x and 10x. A smaller range makes variations appear taller. This setting changes the velocity picture, not the speed commanded to the machine. The status strip reports active-axis count, range and sample count in velocity mode. The graph does not provide the same labelled numerical axes as the dedicated window, so retain those status details when capturing it.

Jitter switches the drawing to start and end timing offsets. The start trace is blue and the end trace is salmon-colored. Its fixed plotting range is −50 to 350 microseconds; the velocity Y slider does not change that timing range. This general scope has no EtherCAT health table or deadline-statistics panel. For numerical timing assessment and explicit simulation status, use Jitter / EtherCAT health.

Read the effective time label

The available time steps begin at 100, 250 and 500 milliseconds, then 1000, 2000 and 4000. Although the slider has further positions, this scope stores at most 4096 samples and caps the displayed effective time at 4096 ms. Trust the visible Time label. It cannot retain a minute of continuous sample history.

With only a small amount of data collected, the scope spreads the available samples across the drawing width. Do not assume that a partially filled capture already covers the entire selected duration. Let a fresh observation collect enough samples before using horizontal spacing to describe timing.

Begin a fresh observation after a gap

Because Pause stops accepting samples in this scope, resuming after the machine has moved can produce an apparent velocity spike at the boundary: the next calculation compares a new position with the last stored position from before the pause. That boundary is not reliable evidence of a physical speed spike. Resume and use Clear before collecting a new continuous observation; preserve any useful earlier screenshot first.

Similarly, do not combine observations from before and after a disconnect or reconnect as if they were one continuous measurement. Start a fresh scope observation. Close and reopen the window if a clean restart is needed, and record the new session context. Neither Clear nor reopening repairs a machine fault.

31.7 Capture useful evidence and respond to unclear graphs

A useful diagnostic capture combines the graph with its context. A waveform alone rarely tells support what the machine was doing, whether the data came from simulation, which axis was selected or how much magnification was applied. Your task is to preserve a clear observation, not to prove a cause from the picture.

Follow a repeatable observation sequence

  1. Define the question. Decide whether you need axis velocity, cycle timing or communication-health information. Select the appropriate window and identify the axes or rows that matter.
  2. Record the starting context. Note operating mode, connection state, current machine activity and the approximate time. For a program-related event, record the program and the visible operation or line information where available.
  3. Set the display before the event. Select a useful time window. For velocity, confirm axis identity and a range that does not clip the expected trace. Clear an earlier local observation only after preserving any useful evidence.
  4. Observe an approved operation. Do not create an overload, unplug a network cable or repeat an unsafe machine action to obtain a more dramatic trace. If reproduction is required, follow the authorized test procedure.
  5. Preserve the relevant view promptly. In a dedicated graph, Pause can hold the displayed event for a screenshot. Remember that the machine continues operating and that the displayed timing assessment is then frozen.
  6. Record limits and finish. State whether data were clipped, stale, incomplete, simulated or interrupted. Close unneeded diagnostic windows and leave the machine in the condition required by the operating procedure.

Capture the whole context, not just the interesting peak

These windows do not provide a built-in operator command for exporting graph data or saving a screenshot. Use the site's approved screen-capture method. Include the title, toolbar, scale, legend and status. For a timing report, capture the health table as well as the graph; take an additional image if scrolling is necessary to show all rows.

Verify that the saved image actually contains the plotted lines. The graphs use a graphics surface that some window-capture methods may omit. A black or empty rectangle in the saved image is not evidence that the original trace was empty. Check the image before sending it and use an approved full-screen capture method if necessary.

When the graph is blank or appears misleading

First distinguish a blank drawing from an unavailable measurement. Check the selected axes, servo-on condition, operating mode, connection state, pause status and sample count. After Clear or a fresh opening, allow samples to arrive. Do not enable equipment solely to populate a graph. In the dedicated plot, OpenGL unavailable identifies a graphics-rendering problem; report that message rather than interpreting it as a controller timing failure.

A stable-looking line can result from a frozen display, a wide scale or lack of new samples. A large-looking variation can result from strong magnification. A clipped peak has an unknown height from the picture alone. Before comparing two images, verify that the window type, axes, time window and scale agree. If they do not, state the differences explicitly.

For an unexpected physical response, use the machine's stop-and-recovery procedure in Chapter 17. For channel-level input and output evidence, use Chapter 30. Keep graph observations, physical observations and suggested causes separate in your report. A precise statement such as “the deadline count increased during this operation” is more useful than an unsupported conclusion that a particular computer or cable is defective.
