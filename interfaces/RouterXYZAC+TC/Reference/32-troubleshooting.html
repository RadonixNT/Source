Messages, Reports and Troubleshooting

Understand a message, preserve its details, find the related session events and choose the appropriate next step.

Expanded draft for review. Troubleshooting starts with the observed machine condition. Acknowledging a message does not repair its cause or confirm that motion has stopped.

32.1 Understand the message before choosing a response

A message is the application's way of telling you about a condition or asking for a decision. Some messages simply provide information. Others explain why an operation cannot proceed, identify a fault, or ask you to confirm an action. Read the complete sentence before choosing a button. The same button label can have different consequences in different questions.

First attend to the machine. If there is unexpected movement, a loose workpiece, a tool problem or another unsafe condition, use the machine's prescribed stop procedure. Do not delay that response while trying to photograph a message. Conversely, do not assume that a message appearing on the screen has automatically stopped all motion. A dialog is an interface notification, not a physical-state confirmation.

Recognize the purpose of the message

Table 32-1. Message categories and an operator's first response
CategoryMeaningFirst response
InformationExplains a condition or operation.Read it and relate it to the action you were performing.
SuccessReports successful completion of the stated operation.Check exactly which operation succeeded; it may be a settings action rather than machining.
WarningA condition needs attention.Read the consequence and required response. A warning is not permission to ignore the condition.
ErrorAn operation failed or could not proceed.Record the message and resolve the stated condition before another authorized attempt.
Critical errorA major subsystem cannot continue safely as expected.Follow the site's stop and service procedure and preserve the details when safe.
QuestionThe application needs an explicit choice.Identify what accepting or declining will do before answering.

The dialog can use a specific title such as Controller or Configuration instead of the category name. Symbols and color help draw attention, but the wording and context determine the meaning. The interface language can also change the button captions. This manual uses the English captions.

Acknowledge, cancel and retry are different actions

In a notice, OK normally acknowledges the message. In a confirmation, it may accept the action described in the question. Yes and No answer that particular question; they are not general machine start and stop controls. Cancel declines or leaves the current request as defined by that operation. It does not undo physical movement that has already occurred.

If Retry is offered, it requests another attempt. Read the recommended action and establish whether the relevant condition has changed before using it. Repeatedly pressing Retry without understanding the failure can obscure the original event and does not repair a sensor, configuration or mechanical problem. Only the buttons provided for that message are available; not every dialog has all these choices.

After dismissing an error, check the main screen and the affected operation again. The message disappearing does not mean the fault is cleared, the tool is clamped, the spindle has stopped or the program can resume. Use the appropriate operation chapter to determine what must be confirmed. When the next action is unclear, preserve the exact wording and seek assistance rather than guessing.

32.2 Expand and preserve message details

The first line of a message is intended to be understandable without technical training. When more information is available, Show details opens a read-only area beneath it. This may explain the condition, suggest a response, show an error code or include technical evidence. You do not need to understand every technical line to preserve it accurately for support.

Use the detail controls

  1. Read the short message and note what you were doing when it appeared.
  2. If Show details is available, select it. Scroll within the details area to read content that does not fit.
  3. Read the recommended action, when supplied. Distinguish an operator check from work that requires service or engineering access.
  4. Select Copy details to place the available detail text on the Windows clipboard.
  5. Paste it into the support note or another approved document and confirm that the intended text was copied. Add the short message and title separately.

Hide details collapses the area again; it does not remove information from the report. The details area cannot be used to edit settings or repair a fault. When a message has no additional details, the extra controls are not displayed. Their absence is not evidence that the message is unimportant.

Table 32-2. Information that may appear in message details
ItemPurposeWhat to preserve
Error codeA stable identifier used to classify the condition.Both the number and the accompanying name, exactly as shown.
Report descriptionA longer explanation than the short message.The full wording rather than a shortened interpretation.
Recommended actionA suggested response to the classified condition.The instruction and whether the authorized check was performed.
Technical detailsOperation-specific evidence, such as a file, device, failed step or internal exception.The complete copied text, even if some terms are unfamiliar.

The copied details are not the whole incident

Copy details copies the assembled details area. It does not automatically add the short message, dialog title, machine activity or an image of the main screen. A support note containing only a technical identifier may therefore be incomplete. Add the exact short message, approximate time, Normal or Simulation mode and the action immediately preceding it.

If copying fails or the pasted text is missing, use a readable screenshot and note the problem. Check the paste rather than assuming the clipboard contains the latest message. For long details, the copied text is usually more useful than several cropped images. Include a screenshot as well when the arrangement of controls or the main-screen condition matters.

Do not confuse a diagnostic identifier with an instruction

An unfamiliar name in the details is normally a label for support, not something you are expected to type into the machine. Do not change a parameter simply because it appears in an error description. When an action requires modifying a mapping, control program, password or drive configuration, use the relevant authorized procedure and access level.

The application normally records diagnostic content when showing a message. Some controller and program notifications have already been recorded, so the dialog avoids writing the same event again. Do not expect a second identical report entry merely because you expanded or acknowledged the dialog. Equally, a missing report line does not invalidate a message you saw; file-writing limitations are explained below.

32.3 Open the current session report and find the relevant event

The session report is a text file containing messages and selected application events. A session normally means one run of the application, from opening it to closing it. Reconnecting the controller during that run does not, by itself, create a new report file. This makes the report useful for following a problem across a disconnect and another connection attempt.

Open it from the application

The command is OpenReportFile. Its supplied shortcut is Ctrl+Shift+Alt+PrintScreen; use the current configured assignment if it has been changed. You can also double-click the main screen's program-progress display. The command asks Windows Notepad to open the current session report. It does not open a built-in searchable alarm-history window.

  1. When machine supervision allows, open the report using the command or the program-progress display.
  2. Note the file name in the editor. Confirm that it belongs to the session in which the event occurred.
  3. Use the editor's Find function to search for a distinctive phrase, error code, operation name or program file name.
  4. Read several entries before and after the match. The first visible error may be a consequence of an earlier rejected request or lost connection.
  5. Preserve the original file. Put your explanation in a separate note or an explicitly separate copy.
Table 32-3. Recognizing the report file
ItemWhat to expect
Usual folder for this product%ProgramData%\Radonix\RouterXYZAC+TC\Report, based on the application's configured product identity. Use the application command to select the current file.
File nameA timestamp followed by .log, for example 2026-10-09 08-30-00.log. This example is illustrative.
Beginning of fileA date/time header. Individual entries normally begin with local time in hours, minutes and seconds.
Restart versus reconnectA new application run uses its own timestamped report name. A controller reconnect within the same run continues the session report.

The editor is not a guaranteed live report viewer

The application writes reports in the background. Opening the report does not force every queued entry to disk, and the command does not refresh an editor that is already showing older contents. If a just-observed event is missing, allow writing to catch up and reopen or reload the file using the editor's available controls. Do not assume that the file visible in an old editor tab is automatically current.

Normal application shutdown attempts to finish writing accepted report entries. An abrupt termination, unavailable storage or logging overload can leave an incomplete report. A diagnostics-queue overflow entry, if present, explicitly indicates that some entries were not accepted. The absence of a line is therefore not proof that an action never occurred.

If no report opens

The command opens the current report only when the file exists. Very early in startup it may not yet have been created; storage or editor-launch problems can also prevent access. Record the exact behavior rather than creating an empty replacement file or deleting old reports. If the problem persists, ask support to check the report location and access to it. Do not restart the machine solely to force a report window to appear.

Notepad is an editor, so avoid typing into and saving over the original report. To share evidence, copy the file to the approved support location and state when the copy was made. A copy taken while the application remains active is a snapshot; later events will not appear in that already-copied file.

32.4 Read the operation sequence without assuming success

A report often records several stages of one operation. A request is the operator's or program's intention. Acceptance means that the software admitted the request. Running, stopping and completion entries describe later observations. Reading only the first positive-looking line can lead to the wrong conclusion about what the machine actually did.

Follow the operation from request to outcome

When investigating a failed start, begin with the relevant Run requested entry and read forward. A later Run accepted entry can explicitly say that positioning or execution is pending. The machine may still need tool preparation and positioning before the work program begins. Acceptance is therefore not the same as cutting having started, and certainly not the same as successful completion.

Table 32-4. Important report wording
WordingWhat it establishesWhat it does not establish
Run requestedA start request was recorded, with its available context.That it passed every condition or produced motion.
Run acceptedThe start was admitted; positioning or execution can still be pending.That the tool has already reached the entry point or cutting has begun.
Program execution runningThe application observed the main program running.Continuous cutting, or the eventual result of the program.
Reset accepted; waiting for motion to stopA stop was accepted and stopping is still being awaited.Immediate physical standstill.
Program execution no longer runningA change out of the running state was observed.Natural completion rather than interruption.
Program completed naturallyThe current execution was reported as naturally completed.Finished-part quality, spindle standstill or completion of a subsequent park operation.
Program execution ended with unknown stop originThe end was observed but its cause was not established.A normal finish or a specific fault cause.

Other outcomes explicitly report a requested stop or an observed axis/coupling fault. Preserve that distinction. If you see only a “no longer running” entry, do not replace it in your report with “completed.” State exactly what was recorded and what you observed at the machine.

Use file and line information as context

Many operation entries include File= and SourceLine=. The file identifies the current program context, and the source line reflects the main path's reported block at the time of the entry. This helps locate the region of an operation. It is not necessarily the exact instruction that caused a later error, nor a guarantee that every preceding line cut material.

Some entries contain more specific information such as a requested start line, a selected line or a named tool-change stage. Keep those fields with the message. A tool preparation or positioning problem can occur while the report still carries the main program's context; it should not automatically be blamed on the visible cutting line.

Read homing and spindle entries carefully

Homing reports can identify an activated routine and its eventual exit reason, result and success indication. An axis home-state change is a separate observation. If homing was interrupted, use Chapter 6 and the actual axis state rather than treating an activation entry as successful homing.

Spindle entries describe output changes and speed setpoints. A recorded RPM setpoint is a command value, not a measurement of shaft rotation. Likewise, an output going off does not prove that the shaft has stopped. Use the machine's required spindle confirmation before tool access; see Chapter 10.

Understand the report's timing limits

The report records selected transitions rather than every control cycle, axis position or program line. Entry times are displayed to the second, so several events can share one time label. Do not use their visible timestamps to calculate millisecond response times. Some notifications are observed after the underlying event, and a loss of connection can interrupt observation.

For timing evidence use Chapter 31; for physical-channel indications use Chapter 30. Combine these sources with the report, but state which evidence came from which view. None is a complete recording of every physical event.

32.5 Use a symptom guide without bypassing the cause

Begin with what you can actually observe: a command is unavailable, a file was rejected, an operation stopped, or a sensor indication did not change. A symptom can have several causes. The table below gives a starting point for operator checks; it is not a diagnosis and does not authorize changing protected settings or bypassing an interlock.

Use the same short sequence each time

First establish the machine's condition and stop the affected operation when required by its procedure. Next preserve the message and approximate time. Then check the relevant main-screen state and read the report around the event. Perform only the normal checks within your authorization. If the cause remains unclear, leave the operation stopped and pass the evidence to the responsible person.

Table 32-5. Symptom, possible explanation and appropriate next step
SymptomPossible explanation to checkOperator response
The controller does not connect.A connection transition is still active, access is missing, settings were rejected, or startup failed.Read the final connection result and details. Confirm the intended mode. Follow Chapter 3; do not repeatedly issue connect requests.
The screen indicates Simulation when real machining is expected.The active connection is simulated.Do not treat simulated motion as hardware verification. Follow the authorized mode-change procedure in Chapter 20.
Run is unavailable.Program loading, homing, positioning, a tool operation, unloading, stopping/reset preparation or another readiness condition is active.Check the current operation and homed state. Use Chapter 16. A disabled button is not a reason to alter limits or control logic.
A program is rejected or no cutting entry can be found.The file has a blocking diagnostic, the requested line is unsuitable, or no valid cutting entry is available.Preserve file and line details. Review Chapter 14 and Chapter 18 before making an approved correction.
The program is no longer running.Natural completion, a requested stop, a fault, an intermediate wait or an uncertain termination must be distinguished.Read the operation state and outcome entries. Use Chapter 17; do not resume solely because an error dialog closed.
A tool change or measurement is rejected or interrupted.Homing/readiness is missing, another tool operation is pending, a preparation stage failed or expected feedback was not confirmed.Record the stage and tool identity. Follow Chapter 11 or Chapter 12. Do not assume the tool is clamped or repeat an exchange blindly.
An output is on but the expected mechanism response is absent.The command and physical confirmation do not agree; wiring, mapping, supply, sensor or mechanical conditions require investigation.Record both output and feedback input using Chapter 30. Do not force outputs to make the picture match.
Configuration cannot be opened or changed.Access requirements, a connection transition, machine activity, a read-only item or validation rules may apply.Use Chapter 21 and Chapter 25. Ask an authorized person rather than seeking a password or interlock bypass.
A time-lock condition blocks operation.The board's lock condition requires the authorized licensing or service procedure.Preserve the message and available board information. Follow Chapter 26; do not change clocks to conceal the condition.
Timing or communication warnings appear.There may be stale data, a non-operational network, a reached deadline or recorded communication faults.Use Chapter 31 to record mode, state and counters. A past nonzero total differs from a growing total.
Configuration cannot be saved when closing the application.The settings save failed, for example because storage or access was unavailable; normal closing can be cancelled.Copy the details and report that the application remained open. Do not force termination and assume settings were saved.

One approved correction, then a controlled check

If the cause is a normal operator condition with a documented remedy, follow that remedy and verify the result through the relevant operating procedure. Record what changed and whether the same symptom returned. If it returns, stop repeating the action and escalate. A different error after a change should also be recorded, not treated as proof that the original cause was fixed.

Do not use a restart as the default cure. It can create a new session report, change the available observation context and require renewed readiness checks. If a restart is part of an authorized recovery, preserve evidence first when practical and follow the normal shutdown and startup procedures. After any interruption, confirm the tool, workpiece, references and restart plan before continuing the job.

32.6 Prepare a service handover and verify an authorized recovery

Ask for assistance when the next action is unclear, the same fault returns, the physical state cannot be confirmed, or the required correction exceeds your access or training. A useful handover lets the next person understand the event without asking you to reproduce it immediately. It should separate what you saw, what the software reported and what you suspect.

Build a small, complete evidence package

Start with a plain-language description: what you tried to do, what you expected, and what happened instead. Add the exact message and copied details. Include the session report from the affected application run, with the approximate event time identified. If several application runs were involved, identify which file belongs to each attempt rather than sending an unexplained collection of reports.

Table 32-6. Service handover template
FieldInformation to provide
Machine and softwareMachine identifier and the installed application version if known; state explicitly if the version is unknown.
Time and sessionDate, approximate local event time, report file name and whether the controller or application had been restarted.
Operating contextNormal or Simulation mode, connection state, loaded program, visible line, selected tool and relevant operation stage.
Expected versus observedThe intended result and the actual screen or physical behavior, described separately.
Exact diagnostic evidenceShort message, code, copied details, relevant surrounding report entries and readable screenshots.
Checks already performedThe approved checks, changes and retries in order, including whether each changed the symptom.
Present machine conditionWhether the job is interrupted, what remains uncertain, and what the next operator must not assume.

Choose supporting views according to the question

For a sensor or output issue, include the full channel address and separate request/feedback indications from Chapter 30. For timing or communication, include the graph settings, assessment and counters from Chapter 31. If support requests control-program activity or memory values, follow Chapter 28 or Chapter 29; do not edit the program to obtain evidence.

Use the site's approved method for sharing the report and relevant program files. Keep an unchanged original and make any explanation or redaction in a separate copy. Never include passwords in the support note. If a file cannot be shared, identify it and describe the limitation so support knows what evidence is missing.

Make uncertainty visible

Write “the release output was on, but I did not confirm tool release” when that is what you know. Do not turn it into “the tool was released.” Similarly, distinguish “the report says Run accepted” from “the machine started cutting.” An honest missing observation is useful information; a guessed result can send the investigation in the wrong direction.

For example, a concise handover could read: “During an authorized tool change, a warning appeared before the return movement. I stopped the affected operation using the normal procedure. The tool's physical clamping state has not been confirmed. The attached message details and session report cover the event at approximately 10:42. No settings were changed.” This is a writing example, not a report of an actual incident.

Recovery requires verification, not just a quiet screen

After an authorized correction, follow the relevant startup or recovery chapter to confirm readiness. Depending on the interrupted operation, that includes the tool state, homing, work reference, workpiece condition and intended restart point. Do not use an arbitrary source line as a shortcut around an unresolved interruption.

Perform only the approved verification operation and observe its outcome. Check both the physical result and the application's state. Preserve any new message or report entry. If the symptom returns, stop further repetition and give support the new evidence alongside the earlier package.

Finish the handover by stating whether the machine has been released for the next operation under the site's procedure or remains awaiting service. Closing a message, reopening the application or obtaining a successful connection is not, by itself, that release decision.
