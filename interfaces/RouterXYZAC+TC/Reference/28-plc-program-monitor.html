PLC Program Monitor

Observe which machine-control programs are loaded or running, read their last reported outcome, and collect useful evidence without changing their operation.

Expanded draft for review. The dedicated PLC programs window is read-only. Its observations complement the machine's normal controls and reports.

28.1 Open the correct monitor and understand its purpose

The PLC programs monitor shows information about the machine-control programs described in Chapter 27. Use it when a technician asks whether a named program is loaded, whether it is running, or what result it last reported. It does not show the cutting path or the current line of a workpiece's G-code file.

The dedicated window is titled PLC programs. Its application command is OpenPlcPrograms, with the supplied keyboard shortcut Ctrl+Shift+Alt+P. Use that combination from the active main window only after checking that keyboard shortcuts are enabled and the saved assignment has not changed. Chapter 24 explains how to inspect the actual assignment.

Opening the window does not start a program

The application creates this diagnostic window when requested. If it is already open, requesting it again brings the existing window forward and restores it if minimized. It does not create another controller connection, start the selected program or restart a completed function. Ordinary command-access restrictions still apply to opening it.

ViewUse it forRecognizing it
Dedicated PLC programs windowReadable program states, scan information and last outcomes.Columns include Program, State, Cost, Scans and Last result.

These views are not interchangeable. If a screenshot shows raw command/status numbers or Draft/RT columns, it is the combined monitor, not the dedicated window described by the column tables in this chapter. State which window you are using when reporting a problem.

Observe without interfering with operation

The dedicated window is a separate, non-blocking window, so the main application can continue working while it is open. This does not mean an operator should take attention away from a machine that requires supervision. Arrange the display so that important operating indications remain visible, or have a second authorized person collect the observation.

The only action button supplied by this monitor is Close. There is no Run, Stop, Enable, Reset or Apply control in this window. Selecting a row is an inspection action. Closing the monitor stops its observation, not the PLC program or the machine. Use the normal machine controls for any actual operating action.

Before drawing a conclusion from the table, first read the footer connection state. An offline catalog is still a list of known program names, but it cannot provide current online execution evidence. The next sections explain how to read the columns and avoid that common confusion.

28.2 Read each column and the footer before interpreting a row

Each row represents one program known to the application's PLC catalog. Read the Program name first and use it as the primary identity in a service report. A number in the first column is useful supporting information, but it is not a tool number, axis number or machining-file line number.

Table 28-2. Dedicated monitor columns
ColumnMeaningDo not confuse it with
#The program's current catalog index.A fixed wiring address or permanent machine-function identifier.
ProgramThe exact program name, such as Background or HomeZ.The workpiece file name.
StateThe reported execution/load condition, with Pending added when appropriate.A complete statement of every enable or access condition.
CostThe scan cost accepted and published for the deployed program.Measured milliseconds, spindle load or a CPU percentage.
ScansThe number of scans executed by the deployed program.Completed parts or the number of separate operator starts.
Last resultThe reported last outcome or fault, sometimes with a numeric result or error.An automatic pass/fail certificate for the physical mechanism.

A scan is a pass through the control logic

During one operation a PLC program may need many scans. It may repeatedly check a condition while waiting for a sensor or delay. Therefore, a large Scans value does not mean that a tool was changed that many times. A continuously active program can accumulate scans while the machine is simply monitoring conditions.

Cost is a software execution-cost value used by the controller's PLC system. It is not a stopwatch reading. If a technician asks for it, report the number together with its column label and program name. Do not describe it as milliseconds or use it to estimate how long a homing move should take.

The footer describes the overall view

The footer shows the controller connection state, the number of catalog programs and, where applicable, Pending changes. The program count is not a count of loaded or running programs. A catalog row can remain present when its executable program is not loaded.

Likewise, the footer's Pending changes is a whole-configuration indication. It need not correspond one-for-one with a Pending label on every row. A shared change can affect the configuration as a whole. Read the selected row and the footer together, then consult the source/configuration diagnostics if a change is being investigated.

When live information is unavailable, Cost, Scans and Last result display a dash. A dash is unavailable information, not zero activity or a successful result. The first two columns can still identify the catalog while the controller is offline.

For a useful screenshot, include the entire selected row and the footer. If the Last result text is clipped, enlarge the window or widen the relevant column before capturing it. Report what the labels actually say rather than inferring information from the row's position.

28.3 Interpret loaded, running, pending and error states

The State cell summarizes selected runtime information. It is not a switch you can change. Start by checking whether the controller is online, then read any Pending addition separately from the execution state. A program can be running while a different source draft is waiting to be deployed.

Table 28-3. State text and practical meaning
StateInterpretation
OfflineLive program information is not currently used by this view. Check the footer for the actual connection state.
Not loadedThe online runtime does not report this program as loaded or running and no higher-priority displayed error is present.
RunningThe runtime reports the program as active.
ErrorA load, start or runtime error is reported. Read Last result and the report.
Blank State cellThe program is reported loaded without running, a displayed fault or a pending source difference.
PendingA configuration/source difference from the deployed version is present; other state text can appear beside it.

Loaded and enabled are different questions

A loaded program has been accepted into the controller's program set. An enabled program is permitted by its program configuration to participate in the appropriate execution. Running means it is actually active. The dedicated monitor does not include an Enabled column or a checkbox, so it cannot be used to toggle enablement.

A blank State cell is therefore not a universal “ready for every command” indication. It reports the loaded, non-running condition described in the table, while command availability, program enablement and machine readiness can still matter. Use the relevant Configuration status or technician's configuration review to investigate enablement.

Pending is not the same as unsaved

The monitor compares the program's current configuration with the deployed version. Configuration can have been saved while the runtime still uses the earlier deployed content. Conversely, editing source can introduce a pending difference before that source is retained in settings. Chapter 27 explains the separate editing, saving, validation and deployment stages.

For example, Running / Pending does not mean the program is about to start. It means the monitor reports current activity alongside a difference from the deployed configuration. Do not assume the text most recently seen in the editor is controlling that active operation.

Offline / Pending combines lack of live execution information with a pending difference. Reconnecting is a separate operating action, not a harmless display refresh. Follow the normal service procedure and review validation results before changing a controller session.

Error takes display priority over Running in this summary. If you see Error, preserve the last-result text and relevant report message rather than trying to infer every internal condition from this single cell. A successful network connection does not erase a program fault, and a visible catalog entry does not prove successful loading.

28.4 Read Last result and distinguish completion from success

Last result explains the most recently reported outcome available to the monitor. It can identify why a program left execution or why a request failed. Read the words before the number. A value shown after “result” and a value shown after a fault message are different kinds of information.

Table 28-4. Last-result wording
TextMeaning for the operator
CompletedThe program's reported activation completed; inspect any additional result value and the physical outcome.
StoppedThe reported activation ended by stopping rather than normal completion.
Start failedThe runtime rejected the activation request.
Runtime faultA fault occurred during execution.
Load failedThe program image was not accepted for loading.
ReloadedThe recorded exit is associated with replacement of the program set.
Controller shut downThe recorded exit is associated with controller shutdown, where that information is available.
DashNo exit outcome is reported in the snapshot, or live information is unavailable.
Unknown outcome followed by a numberThe view cannot translate the reported outcome; preserve the exact text for support.

Completed does not always mean the mechanism succeeded

A program can finish its control sequence and return a nonzero result describing a condition the application must handle. The monitor appends that number, for example Completed (result: 3). This is a format example, not a universal interpretation of result 3.

The meaning belongs to the named program and its installed source. A number used for a timeout in one sequence can describe a different condition elsewhere. Do not apply a result-code explanation from HomeZ to a spindle or tool-handling program merely because the number matches. Report the name, outcome and number together.

For faults, the monitor can append an error number in parentheses after Start failed, Runtime fault or Load failed. Copy that wording exactly. Avoid dropping the distinction between an ordinary returned result and a runtime error when passing the information to a technician.

The last result is not a full event history

This column provides a snapshot of the last available outcome, not a chronological list of every activation. A short function may start and complete between display updates. Another activation can later replace the information. Capture the relevant row and consult the application's report when timing or sequence matters.

If a program is currently Running, do not use a previous Last result as proof that the current operation has already succeeded. Conversely, a dash is not evidence of a fault simply because no completion has yet been reported. Correlate the state with what operation is actually underway.

After a fault, make the machine safe through its normal controls. The monitor has no acknowledgement or reset action that repairs the failure. Record the evidence before undertaking the authorized recovery procedure, especially before a reconnect or program replacement changes the available runtime information.

28.5 Observe cyclic and command programs within the display limits

The supplied catalog contains a cyclic program called Background and command programs used for particular operations. A cyclic program is intended to remain active as repeating control logic when its deployed configuration enables it. A command program becomes active when the relevant operation requests it and normally leaves execution when its task completes or is stopped.

Background being active while no cutting program is running can therefore be normal. It checks machine conditions rather than representing a workpiece job. Its Scans value can continue increasing while the operator is not making a new command request. Do not interpret this as repeated production starts.

Command programs can be brief or remain active while waiting

A command program may wait for a delay, sensor or another machine condition. Remaining Running for a period is not, by itself, a fault. Compare the observation with the expected operation, machine indication and report. If a wait is unexpected, record it without forcing a sensor or editing the sequence.

Table 28-5. Observations that need context
ObservationPossible interpretationUseful check

The monitor samples; it does not record every controller cycle

The dedicated window requests updates on a nominal 200 ms display timer while visible and not minimized. This is a user-interface interval, not the controller's PLC scan time or a guaranteed maximum delay. A busy display system can update later. The table is not an event recorder capable of proving the exact instant of a short transition.

Hidden, minimized and closed diagnostic windows stop their polling. Restoring the window resumes observation. Closing this window does not reset a program's scan counter or stop its execution; it only ends this display's observation. Counters and outcomes belong to the deployed runtime and should not be treated as permanent lifetime production totals.

Online program values are temporarily unavailable in the table during a PLC configuration-application operation. This is one reason to read the footer connection state rather than interpreting every Offline row as a cable disconnection. If the condition persists unexpectedly, preserve the report and controller state for support.

When detailed timing is needed, ask the responsible technician to use the appropriate diagnostic tool. Do not derive sensor response time, control-loop timing or a guaranteed stop time from how fast the words in this table change.

28.6 Use a repeatable observation and reporting procedure

Begin with a question the monitor can answer. For example: “Was the intended homing program loaded?”, “Did the requested command become active?” or “What did this program last report?” A focused observation is more useful than watching the entire table and guessing which changing number explains a fault.

Collect the observation in order

  1. Identify the machine operation being investigated and the expected program name. Use the catalog in Chapter 27 or the technician's instruction.
  2. Open the dedicated PLC programs window and read the footer connection and pending-change information.
  3. Locate the named row and note its State, Scans and Last result before the authorized operation, if available.
  4. Observe the already authorized operation without adding trial commands solely to change the monitor.
  5. Record the resulting row and any relevant report message, including the exact outcome wording and numbers.
  6. If behavior is unexpected, use the normal stopping/recovery procedure and give the collected evidence to the responsible person.

The monitor does not establish that the correct physical sensor changed or that a tool is secure. Combine its program outcome with the operation's normal physical checks and, where appropriate, the I/O diagnostic view. Do not reach into a mechanism to produce an indication while concentrating on this window.

Choose the next investigation from the evidence

If the row is Not loaded, review validation and deployment with the responsible person; repeatedly requesting the operation cannot supply a missing program. If Start failed is reported, preserve the start error and the readiness conditions at the time. If Runtime fault appears, retain the exact fault message and the operation sequence before resetting or replacing anything.

If Running persists unexpectedly, report what condition the machine seems to be waiting for rather than declaring the program frozen solely from this label. If Pending appears after a source change, resolve the saved-versus-deployed version question before drawing conclusions about the new text.

If the monitor looks normal but the physical operation is wrong, a normal-looking software state does not overrule the observation. Report both. The investigation may involve mapping, hardware, timing or the intended sequence, and belongs to the approved service process.

Finish by closing the monitor when it is no longer needed. This does not acknowledge errors, stop programs, save source or deploy changes. Ensure that the handover states what was observed and what remains unresolved. A clear record lets the next person continue from evidence instead of recreating a fault unnecessarily.
